## 1. Enforce Direct-API Request and Supplied-Context Bounds

- Replace the **12 MiB serialized request ceiling / 16 MiB runtime allowance requirement** with a **9,000,000-byte outgoing UTF-8 JSON ceiling**, measured on the actual complete serialized payload before dispatch. This is below the reviewed decimal 10,000,000-byte limit. Apply any independently established lower deployment ceiling explicitly; reject visibly rather than relying on server truncation.
- Keep each text part at **60,000 JavaScript UTF-16 code units or less**. Also bound the **combined normalized text across all request text and trusted system sections to 60,000 code units**, including envelope wrappers, escaped records, source locators and the current instruction. This avoids defeating an aggregate gateway limit by splitting text parts. UTF-16 units conservatively upper-bound Python character count for valid Unicode; reject malformed surrogate sequences and measure the full UTF-8 JSON bytes separately.
- The context builder must select/truncate at source boundaries **before serialization** to satisfy both bounds and the client token budget. Record affected files/history ranges in the persisted coverage manifest and UI, retain originals, and never claim full analysis of omitted text. Mandatory policy/instruction must fit or dispatch fails visibly. Gateway truncation is never the intended budgeting mechanism.
- Keep five normalized JPEG/PNG derivatives at at most **1 MiB each** and approved image dimensions. Their base64 encoding fits within 9 MB with the bounded text envelope, but always measure the final payload, including escaping/metadata. Do not silently drop a fifth image. File eligibility and original retention are unaffected by derivative/context limitations.
- These are **backend-to-Hermes** constraints. Client-to-Kyrae original uploads retain their existing streamed **20 MiB file / 21 MiB multipart-body** route limits and batch aggregate; originals are not sent as runtime JSON. Do not lower upload/proxy limits to 9 MB.
- Retain **24,000 tokens as the Kyrae-supplied-input budget**, using a verified tokenizer or documented conservative text estimate. It is not a bound on Hermes's complete internal prompt/context. Image cost requires a configured evidence-backed safe upper bound and visible accounting provenance; do not fabricate image tokens from byte length. Unknown image/context estimates yield an explicit unavailable profile for live attachment dispatch, while offline development remains possible. Include envelope overhead in selection and keep the 4,096 output reserve/safety allowance as planning reserves, not a proven total runtime context guarantee.

## 2. Replace the Runtime Output Guarantee with an Honest Backend Guard

- The **4,096 model-token output target is requested/intended, not guaranteed by direct Hermes**. Only send supported parameters through an evidenced path; do not assert that a top-level or invented nested `max_tokens` setting controls generation. Configuration/schema inspection may later establish a supported control without changing this guard's truthful semantics.
- Enforce a Kyrae-visible answer cap of **4,096 tokens when a verified serving-model tokenizer is available**. Otherwise use a conservative operational fallback of **16,000 Unicode text code units**, counted as UTF-16 units and cut only at a valid Unicode boundary. This fallback is a finite character guard, **not proof of at most 4,096 model tokens**; expose which accounting mode was used.
- Independently bound the total raw response envelope to **256 KiB**, including JSON/usage/metadata, and bound reads incrementally. Over-limit raw/invalid/incomplete JSON is an explicit failed response unless a validated incremental decoder has already produced safe usable content; never label raw fragments a complete answer. Valid bounded content cut by the token/character guard is returned with **`partialOutput: true`**, a stable reason and a visible partial-answer notice persisted in task/history results. Future shared-contract changes must express these fields before app changes.
- Set an absolute **120-second attachment invocation deadline**, covering connection, headers and the entire response-body read; do not clear cancellation after headers. Abort the read on deadline/byte overflow. Keep the existing indeterminate-dispatch rule: no automatic retry after possible runtime receipt; preserve originals/task outcome and explain timeout/partial status. The prior 90-second probe remains historical evidence, not a successful deadline test.
- **Backend guards do not cap Hermes internal generated tokens, tools, retained artifacts, compute or cost.** Closing a connection is not evidence that remote work stopped. Approving this amendment explicitly accepts that distinction for direct Hermes; it must not be marketed as a guaranteed runtime generation/cost limit. Retain truthful capability reasons and profile metadata rather than promising full internal-context bounds from client accounting.

Unknown runtime privacy/state semantics remain activation/release evidence, not claims already proven by a fresh header.
